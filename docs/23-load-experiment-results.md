# 23. 부하 실험 결과 (진행 중, 2026-09-17)

docs/15 설계의 실행 기록. 각 시나리오는 **같은 입력(SHA256 고정 코퍼스)** 으로 재현 가능하고, 숫자는 전부 `pipeline-load-lab/data/measure_*.csv`·로그에서 나왔다.
성공 기준(docs/15 §5): ① 임계점과 병목 컴포넌트 ② 선행 지표 1개 이상 ③ 개선 1건 전후표 ④ "현 구성 여유 N배" 문장.

## 0. 환경 (실측)
- 호스트: Intel N100 4코어, 15GB(실험 전 used 8 / avail 6). 프로덕션 스택 26컨테이너 동거. **단일 호스트** — 실무의 동일 사양 스테이징이 없어 창·가드·기록으로 축소(docs/15 §7).
- 실험 격리: `load_test.trades`(3p RF2) → 실험 잡 `CDC Realtime Pipeline [load_test]`(lab TM, 1.5g/슬롯 2, 탐지기 비활성) → `load_test_crypto_trades`(TTL 1일). 프로덕션 토픽·테이블·잡 무접촉(매 시나리오 오염 0 확인).
- 코퍼스: Upbit `trades_24h_obs_end.jsonl.gz`(09-15 06:12 기준 24h 체결 create), Binance `binance_5sym_20260915.jsonl.gz`(10,106,013행). SHA256 은 load-lab `data/corpus/SHA256SUMS`.
- 프로덕션 가드: 체결 e2e p95(60초 창) > 30초 3회 연속 → 재생기 kill. 전 시나리오 미발동.

## 1. ① 체결 계단 50 → 100 → 200/s (각 10분, 02:45~03:15 UTC)

| 계단 | 발송/적재 | 백프레셔 max | 소스 busy p50 | CH 적재 rows/s p50 | e2e p50 / p95 / max (s) | CP e2e p95 | Kafka CPU 중앙값 | CH CPU | load1 max |

- 합계 발송 209,999 = 적재 209,999 = uniq(market, sequential_id) 209,999 = uniq(trade_id) → **유실 0, 중복 0**.
- **임계점 미도달**(프로덕션 평시 25~59 rows/s 의 2~8배). e2e 는 유입이 많을수록 낮아지는데 이는 docs/14 §2 의 관찰(배치 창 2s+3s 가 결정, 행이 많을수록 창을 빨리 채움)과 같다.
- 프로덕션 영향: KRW 체결 e2e p95 10분 창 4.68~4.80s(전 30분) → 4.79 / 5.02 / 4.85s(중), max 5.6~8.3 → 8.3~10.5s. 가드 max 8.01s.
- 측정 주의: 컨슈머 lag 은 커밋 오프셋 기준이고 Flink 는 체크포인트(60초)에만 커밋 → **rate×60 의 톱니**(2,953 / 5,931 / 11,980)가 "적체"로 보인다. 적체 판정은 60초 창 최솟값 추세(190→186, 849→836, 1,779→1,613 = 평탄)로 했다. 이 톱니 자체가 대시보드 lag 패널을 읽을 때의 함정이다.
- 한계: 이 계단의 TM 자원 열은 프로덕션 TM 을 찍었다(measure.py 컨테이너 고정 → `--tm-container` 로 수정, 이후 계단부터 lab TM).

## 2. ③ 브로커 단독 상한 (kafka-producer-perf-test, 03:17~03:25 UTC)

토픽 `load_test.perf` 3p / RF3 / minISR2 (프로덕션 체결 토픽과 동일 내구성), 레코드 660B(체결 봉투 실측 크기), acks=all.

| 프로듀서 설정 | 목표 | 달성 | p50 / p95 / p99 지연 |
|---|---|---|---|
| Connect 기본형 (linger 0, batch 16KB, 무압축) | 10k/s | 9,920/s (6.2MB/s) | 12 / 286 / 550 ms |
| 〃 | 30k/s | **19,133/s (12.0MB/s)** | 2,263 / 3,980 / 4,839 ms — 포화 |
| 〃 | 100k/s · 무제한 | 19,187 / 19,271/s | 동일 상한 |
| 배치형 (zstd, linger 20ms, batch 1MB) | 무제한 | **64,956/s (40.9MB/s)** | 37 / 486 / 1,110 ms |

- 결론: 무배치 acks=all 로 약 **19k/s**, 배치 시 **65k/s**. 파이프라인 계단(200/s)의 100~300배 → **Kafka 는 병목 후보에서 제외**. 브로커 3→1 축소(docs/19 #12)를 해도 이 여유는 남는다.
- 한계: 프로듀서 클라이언트가 cdc-kafka-1 컨테이너 안에서 돌아 브로커별 CPU 를 귀속할 수 없고(137~147% 표본은 클라이언트 포함), 4코어를 클라이언트·브로커 3개·프로덕션이 나눠 쓰므로 "브로커 상한"이 아니라 **"이 호스트에서의 상한"** 이다. load1 5.5 → 12.0.
- 프로덕션 영향: 2분 창 p95 4.5~4.8s 유지. 배치형 65k/s 구간(03:24)만 p95 6.2s·max 13.9s. 가드 max 9.19s.
