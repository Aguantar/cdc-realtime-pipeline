# 23. 부하 실험 결과 (진행 중, 2026-09-17)

docs/15 설계의 실행 기록. 각 시나리오는 **같은 입력(SHA256 고정 코퍼스)** 으로 재현 가능하고, 숫자는 전부 `pipeline-load-lab/data/measure_*.csv`·로그에서 나왔다.
성공 기준(docs/15 §5): ① 임계점과 병목 컴포넌트 ② 선행 지표 1개 이상 ③ 개선 1건 전후표 ④ "현 구성 여유 N배" 문장.

## 0. 환경 (실측)
- 호스트: Intel N100 4코어, 15GB(실험 전 used 8 / avail 6). 프로덕션 스택 26컨테이너 동거. **단일 호스트** — 실무의 동일 사양 스테이징이 없어 창·가드·기록으로 축소(docs/15 §7).
- 실험 격리: `load_test.trades`(3p RF2) → 실험 잡 `CDC Realtime Pipeline [load_test]`(lab TM, 1.5g/슬롯 2, 탐지기 비활성) → `load_test_crypto_trades`(TTL 1일). 프로덕션 토픽·테이블·잡 무접촉(매 시나리오 오염 0 확인).
- 코퍼스: Upbit `trades_24h_obs_end.jsonl.gz`(09-15 06:12 기준 24h 체결 create), Binance `binance_5sym_20260915.jsonl.gz`(10,106,013행). SHA256 은 load-lab `data/corpus/SHA256SUMS`.
- 프로덕션 가드: 체결 e2e p95(60초 창) > 30초 3회 연속 → 재생기 kill. 전 시나리오 미발동.

## 3. S3 브로커 정지 5분 (① 100/s 지속 중, 03:33~03:46 UTC, 사용자 터미널에서 실행)

`cdc-kafka-2` 를 `docker stop` → 5분 뒤 `docker start`. 프로덕션 체결 토픽은 RF3/minISR2, 실험 토픽은 RF2/minISR1.

| 시점 | 관찰 (이벤트 로그·REST·ClickHouse·MySQL) |
|---|---|
| 정지 +45s | 프로덕션 토픽 파티션 1 리더 2→1 이동, 3파티션 모두 ISR {1,3}. 클러스터 전체 under-replicated **104 파티션**. 실험 토픽 파티션 0·2 는 ISR 1개(minISR1 이라 계속 기록). Flink 4잡 RUNNING, Connect 2커넥터 RUNNING/RUNNING. 프로덕션 60초 적재 1,178행(정상) |
| 정지 중 5분 | 프로덕션 분당 적재 848~1,265행 연속(빈 분 없음). e2e p95: 정지 순간 03:35 분만 **7.73s(max 10.9s)**, 나머지 4.56~4.84s. Connect 로그 WARN 5건(node 2 연결 불가 2, produce 응답 invalid metadata 1 → 프로듀서가 메타데이터 갱신 후 재시도, 에러 0). 프로덕션 Flink 체크포인트 실패 0, 재시작 0 |
| 재기동 | ISR 완전 회복 **15초 이내**(5초 폴링), 리더 파티션 1 → 2 복귀(preferred leader election). 실험 토픽도 RF2 복귀 |
| 사후 | **프로덕션 무손실**: 정지 전후 trade_id 114,337,320 → 114,350,169 구간 12,849개가 MySQL 12,849 = ClickHouse 12,849. 실험 72,000 발송 = 72,000 적재. 가드 max 7.74s(73표본, 미발동) |

- 실험 잡(lab): 정지 중 lag 60초-최솟값 482→466→461(평탄), 백프레셔 0, 체크포인트 실패 0(e2e max 68ms), 적재 120 rows/s = 입력. e2e p95 4.85~4.90s 불변.
- 왜 무손실인가: Connect 프로듀서는 acks=all + 재시도, 브로커 2대가 minISR2 를 만족한다. Flink 소스는 리더 이동을 메타데이터 갱신으로 따라간다. **설계가 실제로 그렇게 동작함을 처음 실측**했다(docs/19 #12 "형식만"은 디스크 한 장 문제이지 복제 동작 문제는 아니었다).
- 부수 관찰: TM 로그에 `flink-circuit-connect` 컨슈머의 DisconnectException 265건 — 타 프로젝트 잡이 정지된 노드에 fetch 를 반복. 잡 상태는 RUNNING, 데이터 영향 없음(그 잡의 토픽 리더는 다른 노드).
- 측정 주의: "after" 구간 lag 60초-최솟값이 132→967→2,087 로 올라 보였으나 적재율(120/s)과 e2e(4.85s)는 불변이고 최종 72,000/72,000 이다. 60초 창과 체크포인트 주기의 정렬이 어긋나면 최솟값에 커밋 전 값이 남는다. **적체 판정은 lag 이 아니라 "토픽 end-offset − 적재 건수"** 로 해야 한다(다음 시나리오부터).
- 이 시나리오가 브로커 3→1 축소(docs/19 #12)에 주는 답: 1브로커면 이 회복은 없다. 정지 = 프로듀서 버퍼(Connect 는 재시도 한도까지, 그 뒤 태스크 FAILED)와 producer 의 MySQL 원장이 손실을 막아야 한다. 축소 시 그 경로의 실측이 선행 조건.

- 발송 2,099,994 = 적재 2,099,994 = uniq(market, sequential_id) → **유실 0·중복 0**. 프로덕션 오염 0. 재생기 큐 잔량 max 16→42→79(선형, 포화 아님).
- 계단 끝 적체는 rate 와 무관하게 **1.6~1.8초분**으로 일정 — 이건 적체가 아니라 JDBC 싱크 배치 창(3초)에 들어 있는 행이다. 적체 지표는 CSV 의 lag 이 아니라 위처럼 "발행 − 그 시각까지 적재"로 ClickHouse 에서 직접 셌다(§3 교훈).
- **임계점 미도달 (2,000/s = 관찰 주간 피크 시(09시 KST 59 rows/s)의 34배, 평균의 80배)**. 처음 움직인 지표 두 개: ClickHouse CPU 21→34→40%, Flink 소스 busy 48→76→126 ms/s. 둘 다 선형이라 다음 계단(5,000·10,000/s)에서 어느 쪽이 먼저 꺾이는지 봐야 한다 → §5.
- e2e 는 부하가 클수록 낮다(p95 0.99→0.28s). 배치 200행이 0.1초에 차기 때문이고 docs/14 §2 와 같은 기전. "지연이 낮다 = 여유가 있다"가 아니라 "배치가 빨리 찬다"로 읽어야 한다.
- 프로덕션 영향: KRW e2e p95 10분 창 4.69~5.01s, max 8.4→5.6s(오히려 전보다 낮음), 가드 계단별 max 6.07 / 5.06 / 5.05s. 프로덕션 CDC 잡 체크포인트 실패 0. 실험 잡 체크포인트 127/0, 상태 6.7KB(탐지기 없음).
- 측정 도구 사건(03:57): kafka-1 CPU 147% 의 정체가 measure.py 의 `docker exec` CLI JVM(5초마다 2개, 각 ~1코어 2초)이었다. 브로커 프로세스는 23%. confluent_kafka 클라이언트로 교체하고 측정기만 바꿔 끼웠다(재생기·가드 유지, CSV `_b` 03:57:29 이후). **①·③·S3 의 브로커 CPU 열은 같은 오염이 있어 브로커 값으로 읽으면 안 된다**(이 절의 브로커 CPU 는 교체 후 값).
- 재생기 버그 1건: rate 모드 `time.sleep(target − now)` 가 `time.time()` 두 번 호출 사이 음수가 되면 ValueError(10k/s 드라이런에서 발견) → `max(0, …)`. 10k/s 드라이런 60초: 9,999/s 유지(파이썬 재생기 자체는 10k/s 까지 병목 아님).
