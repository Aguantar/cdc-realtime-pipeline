# 18. 2026-09-16 발견 정리 — 무엇을 찾았고, 왜 그렇게 찾았나

하루(UTC 06:10 ~ 12:00) 동안 7일 무변경 관찰을 닫고, 이상탐지 기준을 갈아엎고, 원장 대조를 DAG 로 올리고, 그 DAG 가 잡아낸 유실 두 건을 복구했다.
상세는 docs/14·16·17 에 있다. 이 문서는 **발견 자체와 그 발견에 이른 방법**을 한곳에 모은다. 커밋 20개, 근거 쿼리는 docs/16-appendix 에 재실행 가능한 형태로 있다.

## 1. 데이터로 뒤집힌 결론 (이 날의 핵심)

### 1-1. "지표가 좋으면 데이터도 맞다"가 거짓이었다
관찰 7일 동안 원장 대조는 **6일 연속 가중 비율 100.0%** 였다. 그런데 같은 데이터를 DAG 로 옮겨 첫 실행을 하자 유실 두 건이 즉시 나왔다.

| 유실 | 규모 | 왜 안 보였나 |
|---|---|---|
| KRW-BFC 6일 무수집 | 261,713건 (전량) | 관찰 cron 이 **비교할 마켓 목록을 ClickHouse 에서** 가져왔다. 우리가 안 받은 마켓은 목록에 없으니 분모에서 통째로 빠진다 |
| 재연결 5초 구멍 (09-15 20:47) | 45초 창의 160건 = **16.06%** | 하루 가중 비율로는 99.3% 이상이라 임계에 안 걸린다. 셀(마켓×시간) 단위로 봐야 TIA 50.6% 가 보인다 |

덧붙여 오늘 배포를 위한 컨테이너 재기동 **2초**도 30초 창에서 22건(4.19%)을 날렸다(복구 완료).
5초 → 16.06%, 2초 → 4.19%. **재기동 1회가 곧 데이터 손실**이라는 뜻이고, 그래서 이날 이후 미용 목적 배포는 보류했다(§5).

**교훈은 임계값이 아니라 분모다.** 대조의 기준 목록을 우리 쪽에서 만들면, 우리가 못 본 것은 영원히 못 본다.
새 테스트는 마켓 목록의 기준을 **거래소**로 두고, 비율 테스트와 별도로 "거래소에 거래가 있는데 우리는 0건" 커버리지 테스트를 분리했다.
유실은 비율로 나타나지만 **구독 누락은 부재로 나타나기** 때문이다.

### 1-2. 백필이 스트림 상태를 오염시킨다 (기전을 처음 특정)
20:47 구간 백필(160행) 직후 알림 10건. 체결 시각으로 가르니 정확히 반반이었다.

| 묶음 | 예 (KRW-LIT) |
|---|---|
| 백필된 옛 체결 5건 | 11:31 탐지, 체결 09-15 20:47:01, "급락 5,915 → 5,515 (6.76%)" — 6일 전 체결을 **현재가**와 비교 |
| 직후 실시간 체결 5건 | 11:33 탐지, 체결 09-16 11:33:24, "급등 5,515 → 5,910 (7.16%)" — 실시간 체결이 **백필된 옛 가격**과 비교되어 되튐 |

`AnomalyDetector` 가 마켓별 `lastPrice` 를 keyed state 로 들고 직전 체결과 비교하므로, 백필 행이 같은 토픽으로 끼어들면 상태가 과거 값으로 덮인다.
**한 번의 백필이 두 번 오탐을 만든다.** 09-10 백필의 1,687건도 같은 기전이었으나 그때는 "7일 전 가격 비교"로만 적고 기전을 특정하지 못했다.
BFC 백필(138건)에서는 되튐이 없었다. 그 마켓은 애초에 미구독이라 끼어들 실시간 스트림이 없었다 → **구독 중 마켓을 백필할 때만** 발생한다.

세 번 재현됐다: 09-10 백필 210,469행 → 1,687건(당시 기전 미특정), 20:47 백필 160행 → 10건(5쌍), 재기동 백필 22행 → 2건(1쌍).
**백필 1건이 오탐 2건**이라는 규칙성이다.

이 발견이 다음 설계를 바꾼다. 재연결 gap-fill 을 그대로 자동화하면 메울 때마다 알림이 두 배로 튄다.
선택지: (a) `is_backfill` 플래그로 알림만 억제 (b) 이벤트 시각이 처리 시각보다 N분 이상 늦으면 알림 생략 (c) 백필 전용 토픽·잡 분리.
(b) 를 권장한다 — 가장 단순하고 gap-fill 뿐 아니라 지연 유입 전반에 적용된다.

### 1-3. 이상탐지 기준에 근거가 없었다
코드 주석은 세 규칙을 "업비트 시세관여·체결관여·매매집중 대응"이라고 설명했다.
업비트 이상거래 감시정책 원문(PDF 7쪽)을 읽으니 그 7유형은 **전부 계정·주문 단위 관여율**이다. 공개 체결·호가로는 계산할 수 없다.
이름만 빌렸고, 숫자(3%, 1억, 150배)는 "시간당 30~50건 나오게" 맞춘 값이었다.

대안으로 **업비트 시장경보제도(주의/경고/위험)** 를 재현 대상으로 잡았다. 자동 지정·해제이고, 지정 결과가 API 로 내려오므로 정답 데이터가 된다.

| 규칙 | 도출된 기준 | 실측 |
|---|---|---|
| 가격 급등락 | 24시간 전 대비 **±50% 주의 / ±100% 경고 / ±200% 위험** | 지정 시각 지표 중앙값 51.7% / 101.2% / 196.9%. 역검증: ≥50% 인 분 3,221개 중 3,220개가 지정 구간 안 |
| 거래량 급등 | 전일 거래대금 ≥ 7일 평균 × 4 AND ≥ 10억 | 6개월 1,981 라벨 대비 정밀도 0.79 / 재현율 0.80 (30일 평균 기준은 0.57/0.60) |
| 입금량·소수계정 | 계산 불가 → 거래소 지정을 그대로 표시 | 온체인·계정 데이터 필요 |

**숫자를 내가 고르지 않았다.** 거래소가 지정한 순간의 지표값 분포가 임계를 알려 줬고, 반대 방향(임계를 넘었는데 지정 안 된 경우)으로 한 번 더 검증했다.

## 3. 같은 실수를 두 번 했다 — 부재를 단정하는 것

| 시점 | 단정 | 실제 |
|---|---|---|
| 09-10 | "유실은 업비트 WS 가 버스트에서 안 보내는 것" | 독립 수신기 실험 → **우리 파이프라인의 유니크 키 버그** (docs/13) |
| 09-16 | "주의 경보 지정 이력은 어디에도 없다. 2~4주 라벨을 모아야 한다" | 웹 번들 추적 → `crix/market-event-records` API → **6개월 15,588 에피소드**, 대기 불필요 (docs/16) |

두 번 다 사용자가 "정말 그런가" 되물어서 뒤집혔다. 두 번째는 첫 번째를 근거로 되물었다 —
"저번에도 업비트 api 문제라고 했던 거 결국 우리 파이프라인 문제였잖아".

그래서 원칙을 명문화했다. **부재·외부 귀책 결론은 다음을 다 본 뒤에만 말한다.**
공식 API 문서 밖의 웹 클라이언트 네트워크 호출(JS 번들의 경로 문자열), 우회 API(Zendesk 등), Wayback CDX, 공지 API, 그리고 독립 재현 실험.
이번에 실제로 쓸모 있었던 것은 **JS 번들의 경로 문자열**이었다. Wayback(45회 캡처)·공지 API·텔레그램·깃허브는 전부 헛다리였고, 그 사실도 기록해 뒀다.

부수적으로, 문서에 적혀 있던 주장도 실측 전에는 믿지 않기로 했다.
"업비트는 최신 구독 메시지로 교체"는 09-10 worklog 에 적혀 있었지만 검증한 적이 없었다 → 프로브로 1마켓 → 3마켓 → 1마켓을 보내 교체·연결 유지를 실측한 뒤에 구현했다.

## 4. 관찰이 알려 준 것 (docs/14 요약)

- **피크가 가장 빠르다.** 유입 최대인 KST 09시가 지연 p95 2.05초로 최저, 유입 최소인 새벽이 2.4초로 최고.
  자원이 아니라 **배치 창**(producer 2초 + Flink 3초/2초)이 지연을 결정한다는 뜻. 다음에 지연을 줄이려면 손댈 곳이 정해졌다.
- **증가와 누수는 증가율로 구분되지 않는다.** MySQL 행수가 258만 → 1,625만으로 6배가 됐지만, "지워졌어야 하는데 남아 있는 양"은 3,205행뿐이었다. 정리는 따라가고 있고 증가는 과도기였다.
- **디스크 +35.7GB 중 30GB 는 설계된 증가**(Kafka 보존 창이 차는 과정). 나머지가 정리 대상.
- **계획한 변경을 취소하는 것도 결정이다.** 호가 TTL 머지가 10,079,767행 12.8초·65MiB 로 싸게 끝나, 켜기로 했던 `ttl_only_drop_parts` 를 근거 소멸로 철회했다.
- **관찰 데이터의 예외는 지우는 게 아니라 표시한다.** 백필 창 80분을 지연 통계에서 제외하되, 제외 사실과 이유를 문서 맨 위에 적었다.

## 7. DE 관점에서 이 날의 가치 (냉정하게)

**강한 신호**
- 품질 게이트가 **실제로 실패하고, 원인을 짚고, 고친 뒤 통과한** 기록이 남았다. 통과만 하는 테스트는 증거가 아니다.
- "지표가 100% 였는데 데이터는 틀렸다"는 사례와 그 구조적 원인(분모를 우리 쪽에서 만들었다)을 설명할 수 있다.
- 임계값을 **정답 데이터 대비 정밀도·재현율로 정당화**했고, 그 과정을 재실행 가능한 스크립트로 남겼다.
- 자기 결론을 표본 독립성·독립 데이터·라벨 정렬 민감도로 스스로 감사했다.
- 스트림 상태 오염처럼 **배치와 스트림이 한 토픽을 공유할 때 생기는 문제**를 기전까지 특정했다. 이건 실무에서 반복해서 만나는 계열의 문제다.

**약한 부분 (인정해야 할 것)**
- 1층 규칙은 거래소 플래그의 재현이다. 누구나 API 로 받을 수 있는 것이므로, 가치는 재현 자체가 아니라 **선행 시간**에 있고 그건 아직 안 쟀다.
- 알림에 여전히 받아서 행동할 사람이 없다. 이상탐지의 정의는 본래 도메인 팀 몫이고, DE 가 만드는 것은 그들이 정의·검증·배포할 수 있는 기반이다.
- 규모는 여전히 작다. 하루 250만 건은 단일 호스트로 감당되는 수준이고, 포화 지점은 부하 실험(docs/15)에서 확인해야 한다.

## 8. 결정 대기

1. **gap-fill 방식** — (a) `is_backfill` 플래그 (b) 늦은 이벤트 알림 생략 (c) 백필 전용 토픽. (b) 권장.
2. **이상탐지 규칙 교체** — 기존 3규칙 삭제, PRICE_24H·VOLUME_24H·EXCHANGE_FLAG 로. 섀도 1주 뒤 승격.
3. `markets` 상태 테이블(상장일·폐지일·경보) — 마켓 마스터이자 CDC 를 쓸 자리.

## 부하 실험에서 얻은 측정 교훈 (2026-09-17 추가, docs/23)
| 교훈 | 무엇이 있었나 | 어떻게 바꿨나 |
|---|---|---|
| 컨슈머 lag 은 적체가 아니다 | Flink 는 체크포인트(60초)에만 오프셋을 커밋해 lag 이 rate×60 톱니로 보인다. 10k/s 에서 60만까지 | 적체는 "토픽 발행 − ClickHouse 적재"로 직접 센다. 60초-최솟값도 체크포인트 정렬에 따라 착시 |
| 측정 도구가 실험을 흔든다 | `docker exec cdc-kafka-1 kafka-*` 가 5초마다 JVM 2개를 띄워 브로커 CPU 열이 147%. 브로커 자체는 23% | confluent_kafka 클라이언트로 오프셋 읽기. 관찰 cron 도 같은 오염이 있음을 기록 |
| 완료·종료 판정은 산출물로 | `pgrep -f`/`pkill -f` 가 대기 중인 자기 셸에 맞아 6분 오판·검증 셸 종료(exit 144) | 로그의 exit 코드·최종 JSON 으로 판정, 패턴은 `^python3 replay/…` 앵커 |
| 백프레셔 0 ≠ 여유 | 소스가 체인의 머리라 10k/s 포화에서도 backpressure 0 | 소스 busy(ms/s)와 싱크 지연을 본다. health_check 에 그 둘을 넣음 |
| "지연이 낮다 = 여유" 아님 | 부하가 클수록 e2e 가 낮아짐(배치가 빨리 참) | 지연은 배치 창의 함수. 여유는 busy·적체로 |

## 되돌릴 수 없는 데이터를 가리는 법 (2026-09-17 추가, docs/23 §7)
| 교훈 | 무엇이 있었나 | 어떻게 바꿨나 |
|---|---|---|
| "무손실"은 경로별로 따로 말해야 한다 | S3(브로커 1대 정지)의 무손실은 체결 경로 이야기였다. 브로커 전체 정지에서 체결은 3,307=3,307, 호가는 35,838 전부 유실 | 문서의 무손실 문장에 항상 경로를 붙인다. 원장이 있는 경로(체결)와 없는 경로(호가)를 구분 |
| 되돌릴 수 없는 쪽이 더 두꺼워야 한다 | 원장이 없는 호가 경로가 수집기→Kafka 직행·버퍼 120초·대조 수단 없음으로 가장 얇았다. 사용자가 짚기 전까지 체결에만 안전망을 쌓았다 | 유실 창 기록 모델 + 버퍼 600초 + 메타데이터 대기 300초. 스풀(로컬 원장)은 다음 정지에서 한계가 보이면 |
| 예상한 원인이 작고, 예상 못 한 원인이 컸다 | 타임아웃(1.45만)보다 브로커 재기동 순간의 메타데이터 블립 폐기(2.1만)가 더 컸다. 실측 전엔 타임아웃만 고치려 했다 | 고칠 값을 정하기 전에 실측한다는 원칙이 여기서 두 번째 원인을 찾았다. "정지 중"만이 아니라 "복구 순간"도 잰다 |
| 도구가 먼저 있어야 사건이 기록된다 | 실측 전에 만든 유실 창 모델이 정지를 자동으로 잡았고, 30일 전수에서 09-12 6초 유실도 처음 드러났다 | 되돌릴 수 없는 데이터엔 "얼마나 잃었나"를 세는 표를 먼저 둔다 |
| 축소 결정의 본질은 브로커 수가 아니다 | 3→1 질문은 "호가를 어디까지 지킬까"였다. 3브로커의 의미는 내구성이 아니라 장애 처리 경로(리더 이동·ISR·재시도)가 실제로 동작함을 확인한 것 | 축소 전 조건 = 호가 경로 수정의 실측 검증(1분 정지 재실험) |
