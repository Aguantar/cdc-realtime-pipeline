## 블로그 3편 제안 (리듬 유지)

1. **"유실인 줄 알았던 지연" (에피 2 + 3)** — 거래소 시각과 적재 시각을 나눠 보는 순간 사고의 정체가 바뀐 이야기. Flink 상태 625MB의 정체까지 "지표가 보는 곳이 잘못됐다"는 한 주제.
2. **"3%가 조용히 사라지고 있었다" (에피 9)** — 원장 대조 → 오판 → 독립 수신기 → 스키마 → 백필. 틀린 결론을 실험으로 뒤집은 과정과 백필 실수까지 그대로.
3. **"7일 동안 아무것도 바꾸지 않기" (에피 7·8·10·12)** — 실측으로 용량표를 갈아엎고, 가설을 먼저 적고 관찰하고, 결정을 근거와 함께 남긴 이야기. 실무 관행과의 차이(단일 호스트, 인위적 CDC 소스)를 인정하는 톤.

## 17. 임계점을 찾다 (2026-09-17)
- 녹화-재생 부하 실험 5시나리오: 50~200/s 무변화 → Kafka 단독 19k/65k msg/s → 브로커 1대 5분 정지 무손실(MySQL 12,849 = ClickHouse 12,849) → 2,000/s 무변화 → 5,000/s 실시간, **10,000/s 에서 정체**(e2e p95 26.5s).
- 병목은 예상(ClickHouse)과 달리 **소스 체인에 묶인 동기 JDBC 싱크**: 서브태스크 busy ≈ inserts/s × insert 지연, 파티션 3개/서브태스크 2개 편중. 배치 200→1,000 한 줄로 정체 5→0, e2e p95 26.5→0.28s.
- 측정 도구가 실험을 흔든 사건 3건: lag 톱니(체크포인트 커밋), docker-exec CLI JVM 이 브로커 CPU 147% 로 보임(브로커는 23%), pgrep/pkill 자기 셸. "0 이면 안 됐다"·"지연이 낮으면 여유"·"백프레셔 0 이면 여유" 셋 다 틀린 직관.
- 동거 부하 분리: 정체가 "언제" 터지는지는 MySQL 정리 이벤트(10분마다 DELETE 4만)가 정했다. 타 프로젝트 영향 없음.
- 문서: docs/15 §7, docs/23. 블로그 8편 후보 — "여유 85배라는 문장을 만들기까지".

## 18. 되돌릴 수 없는 데이터는 어느 쪽인가 (2026-09-17)
- 브로커 3→1 축소를 묻다가 사용자 통찰: "호가가 원래 DE 가 기대하는 되돌릴 수 없는 데이터 아닌가". 맞았다 — 체결은 MySQL 원장 + 거래소 REST 이중 안전망, 호가는 둘 다 없음. 그런데 호가 경로가 더 얇았다.

- 실측 전에 유실 창 기록 모델(`dq_orderbook_gaps_daily`)을 만들어 두어, 이 정지가 "06:38:50 +216s·추정 38,664" 로 자동 기록됐다(실제 35,838). 30일 전수에서 09-12 의 6초 유실도 처음 드러남.
