## 2. 냉정한 판정
**브로커 자체는 문제가 아니다. 문제는 "메시지를 어떻게 만들고 무엇을 약속하느냐"에 있고, 그중 셋은 이미 실측 피해가 있다.**

| # | 지점 | 왜 부적절한가 (근거) | 어떻게 |
|---|---|---|---|
| 1 | **체결 키 = trade_id** | 파티션 3개에 마켓이 무작위로 흩어져 **마켓 내 순서가 깨진다**. 재정렬 5.87%/최대 4.8s(docs/20)의 원인이고, 탐지기의 "종가 정의" 버그(docs/22 §4-4)도 여기서 왔다. 도메인 관점에서 체결의 자연 키는 마켓이다 | Debezium `message.key.columns=crypto_db.crypto_trades:market` → 같은 마켓은 같은 파티션, 순서 보장. A-1 과 같은 창(어차피 키 설정을 바꿈). 편중은 BTC 518건/분 수준이라 문제 없음 |
| 2 | **처리 시간 창(체결 5분 집계)** | 재기동·정지 뒤 따라붙는 행이 "지금" 창에 들어가 과거 5분이 왜곡된다. 호가는 이벤트 시간인데 체결만 처리 시간 — 일관성 없음 | 이벤트 시간 창 + 워터마크(호가와 동일). `trade_aggregations` 는 dbt 마트(docs/27)가 대체하고 있어 폐기도 선택지 |
| 3 | **압축 없음·bytes 보존** | 800B JSON 을 그대로 → 디스크 10GB, 재처리(docs/28 §2) 하려면 시간 기준 보존이 필요한데 bytes 라 "며칠치"를 보장 못 한다 | 토픽 `compression.type=zstd`(3~5배), `retention.ms=7d` + bytes 상한 |

| 5 | **스키마 계약 없음** | 생산자가 컬럼을 바꾸면 하류가 런타임에 깨진다. A-1 이 컬럼 3개를 추가하는 첫 실전 | 최소: 버전 있는 JSON 스키마 파일 + CI 검증(생산자·파서 양쪽). 정석: 레지스트리(Avro/Protobuf) — KRaft 컷오버와 묶음 |
| 6 | JMX exporter 없음 | 브로커 지표를 CLI 로 찍다 실험을 오염(docs/23) | kafka JMX exporter → Prometheus |
| 7 | 격리·보안 | 타 세입자와 쿼터 없이 동거, PLAINTEXT | 단일 호스트에선 수용. 문서에 명시 |

**괜찮은 것**: 토픽 이름 규칙(`cdc.<db>.<table>`, `upbit.orderbook.v1` 버전), 호가 키·압축·이벤트 시간, 멱등 프로듀서, Flink 체크포인트 오프셋, at-least-once + RMT, RF/minISR 결정의 근거(docs/24).

## 5. 격리·보안 — 위협 모델로 다시 (사용자 질문 "비용 때문에 안 한다는 게 합당한가", 09-19)
"비용"만으로는 근거가 아니다. 장치마다 **무엇을 막는지**와 **그 위협이 여기 있는지**로 판단한다.

| 장치 | 막는 것 | 우리 위협 | 판정 |
|---|---|---|---|
| TLS | 네트워크 구간 도청·변조 | 클라이언트·브로커가 한 호스트의 도커 브리지 안. 신뢰 안 되는 구간 없음 | **안 함** (근거 있음) |
| ACL/SASL | 승인 안 된 클라이언트의 읽기·쓰기·관리 | 같은 호스트의 타 프로젝트는 같은 소유자. 문제는 **LAN** — 실측: `192.168.219.114:9092` 에서 무인증으로 토픽 12개 조회 가능. 광고 리스너가 localhost 라 데이터 조작은 어렵지만 **Connect 8083(커넥터 삭제·설정 변경)·Flink 8081(잡 취소)·ZooKeeper 2181 은 LAN 에서 그대로 조작 가능** | **노출 차단 필요**. 인증 대신 바인딩/방화벽이 맞다(닿을 필요가 없는 포트는 닫는 게 인증보다 싸고 확실) |
| 쿼터 | 세입자 하나의 폭주로부터 나머지 보호 | 타 프로젝트 0.2~1.3%, 부하 실험은 격리 토픽·TM. 폭주 이력 없음 | 안 함, 세입자가 커지면 |

조치 (ClickHouse 8123 때(docs/21)와 같은 부류, 그때는 wg0 기동 순서 때문에 미뤘지만 이 넷은 Oracle 이 쓰지 않아 제약 없음):
1. 즉시(사용자, sudo): DOCKER-USER 체인에 LAN → 9092/2181/8083/8081 차단, 호스트 자신(127.0.0.1)·도커 브리지·wg0 은 허용.
2. 다음 재기동 창: compose `ports` 를 `127.0.0.1:9092:9092` 등으로 바인딩(kafka-1 재기동은 14초 정지 실측). ClickHouse 8123 은 n8n(wg0) 때문에 `127.0.0.1` + `10.88.0.2` 두 바인딩.
검증: LAN IP 로 접속 실패, 호스트 안 클라이언트·Oracle n8n 정상.

## 6. KRaft 로 바꾸면 다시 해야 하나 (사용자 질문, 09-19)
| 항목 | KRaft 컷오버(docs/24 B, 새 클러스터) 때 | 이유 |
|---|---|---|
| 방화벽·127.0.0.1 바인딩 | **유지**. ZooKeeper 2181 이 사라지고 KRaft 컨트롤러 포트가 생기면 목록만 갱신 | 포트 기준 규칙이라 브로커 방식과 무관 |

| zstd·7일 보존 | **다시 적용** — 새 클러스터엔 토픽이 새로 생기므로 | 토픽 설정은 클러스터 안에 산다 → **토픽 정의를 코드로**(`scripts/ops/kafka-topics.sh`: 이름·파티션·RF·압축·보존)로 두고 지금과 컷오버 때 같은 스크립트를 실행 |
| 파싱 DLQ·스키마 계약·JMX exporter | 유지 | 코드·CI·exporter 는 클러스터와 무관(exporter 는 대상 주소만) |
