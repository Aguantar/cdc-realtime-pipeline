### 1-1. 왜 놓쳤나 — grep 은 Grafana DB 안을 못 본다
docs/34 #3(시간 규약 통일)에서 `trade_date → day_kst`, `hour_start → hour_kst` 로 바꾸면서

→ 교훈: **열 이름을 바꿀 때 소비자 목록은 저장소가 아니라 "그 열을 읽는 모든 주체"** 다.

대체재(`ops_metrics_5m`, 5분 cron 호스트 지표)는 docs/32 에서 이미 만들어 뒀는데 대시보드만 안 옮겼다.

## 3. 대시보드를 만들다 잡은 진짜 버그 — 3자 대조가 열린 날에 항상 틀렸다
품질 패널을 붙이자마자 **오늘치 원장 3자 대조가 5심볼 전부 불일치**로 떴다(어제는 0).
실제 데이터를 세어 보니 MySQL 479 = ClickHouse 479 로 **멀쩡했다.**

원인: 비교하는 두 값의 **측정 시각이 달랐다.**
- `my_*`(MySQL·거래소) = 생성기가 매시 남긴 스냅샷 → 그 시각까지의 값
- `ch_*`(ClickHouse) = dbt 실행 시점의 **현재** 값

그 사이에 낸 주문 9건/심볼이 통째로 차이로 잡혔다. 즉 **열린 날은 구조적으로 항상 불일치**였다.
(`quality_alerts` 는 `day_utc < today()` 라 거짓 알럿은 안 났지만, 대시보드에는 그대로 보였다.)

고침 — 자르는 기준이 열마다 다르다는 것이 핵심이었다:

| 열 | 기준 |
|---|---|
| 주문 수 | `created_ms ≤ 마지막 대조 시각` (MySQL 도 '생성'을 센다) |
| 상태 집계(체결·취소·수량) | `updated_ms ≤ 마지막 대조 시각` |
| 체결 수 | `filled_ms ≤ 마지막 대조 시각` |

1차로 주문 수만 맞췄더니 5 → 2 로 줄었고, 남은 2건은 **기준시각 전에 생겼지만 그 뒤에 체결된 주문**이었다
(BTC·SOL 각 1건). 상태 집계까지 같은 시각으로 자르니 **0**.

## 5. 재편 — "어떻게 만들었나"가 아니라 "무엇에 답하나"로 (11:15 ~ 11:40 UTC)

> 사용자: "파이프라인 관측 및 오류 탐지용 1개, 이상탐지 1개 이렇게 각각 만드는 건 어때? … 근데 전자랑 airflow 랑 겹치나?"
> **겹쳤다.** 그리고 그게 원래 구조의 문제였다.

### 5-1. 겹침을 세어 봤다
대시보드가 **만들어진 경위**(원본 / dbt / 운영)로 나뉘어 있어, 같은 주제가 여러 곳에 흩어져 있었다.

| 주제 | 어디에 있었나 |
|---|---|
| 유입 | 메인 2패널 + 운영 1패널 |
| 지연 | 메인 2 + 품질 1 + 운영 3 |
| 이상탐지 산출물 | 메인 2 + 품질 1 + DBT 3 + 운영 1 |
| 시장 데이터 | 메인 4 + DBT 10 |

보는 사람은 만들어진 경위를 모른다. **"지금 파이프라인이 멀쩡한가"와 "시장에 뭐가 터졌나"** 두 질문으로 찾는다.

### 5-2. 두 개로
| 대시보드 | 답하는 질문 | 구성 |
|---|---|---|
| **파이프라인 관측 · 오류 탐지** (23패널) | 지금 제대로 도는가 | ①지금 상태 ②유입(두 거래소 네 경로) ③지연(종단·적재·CDC 구간) ④정확성(Upbit·Binance·원장 3자) ⑤오류·공백(늦은 행·수리 계보·공백 라벨·토픽 계약) ⑥자원·알럿 |
| **이상탐지 (시장 경보)** (18패널) | 무엇이 언제 지정됐고 그 판정이 맞나 | ①지금 지정 상태 ②전이 ③규칙 평가(정밀도·재현율·선행) ④거래대금 급등 ⑤마켓 상태 + 시장 맥락 |

읽는 순서를 섹션 번호로 박았다. ③지연을 종단·적재·CDC 구간 셋으로 나눈 이유는
**구간을 나눠야 병목이 어디인지 말할 수 있기** 때문이다(docs/08 적재 지연 36.9시간 사고의 교훈).

**패널은 옮긴 것이지 다시 쓴 것이 아니다.** 이미 검증한 SQL 을 그대로 들고 자리만 새로 줬다 —
재작성하면 오타로 새 버그가 생긴다. 내려간 정의 3개는 `grafana/archive/` 에 이유와 함께 보관했다.

## 6. 가시성 개선 — 왜 "난잡하고 즉각적으로 안 들어왔나" (2026-09-20 14:40 ~ 15:00 UTC)

> 사용자: "이전 대시보드가 조금 더 가시성이 좋았어. 지금은 좀 난잡하고 즉각적으로 안 들어와."

맞았다. 보관본(`grafana/archive/cdc-pipeline.json.bak.20260920`, 2월판)과 비교해 **원인을 찾았다.**

### 6-1. 원인 — `fieldConfig` 가 비어 있었다
| | 2월판 | 내가 만든 것 |
|---|---|---|
| `unit` | `ms`·`currencyKRW`·`locale` | **없음** |
| `thresholds` | green/yellow/red 3단 | **없음** |
| `color.mode` | `thresholds` | **없음** |
| `options` | `colorMode: background`, `graphMode`, `reduceOptions` | **`{}`** |

설정이 비면 Grafana 는 **단위 없는 회색 숫자**를 그린다. `4.64` 가 초인지 밀리초인지, 정상인지 위험인지
화면만 봐서는 알 수 없었다. 값은 맞는데 **읽을 수 없는** 상태였다.

**조치**: 패널마다 의미에 맞는 단위·임계·색을 넣었다. 임계는 근거가 있는 값으로.

| 패널 | 단위 | 임계 근거 |
|---|---|---|
| e2e p95 | `s` | 30초 = SLO(docs/32) |
| load1 | — | 3.5 / 6 = 코어 4 기준(주간 다이제스트와 동일) |
| Flink busy | `ms` | 500 경고 / 1000 포화(docs/23 §5) |
| 대조 비율 | `percent` | 99.9 미만이면 빨강 — 알럿 임계와 같게 |
| Flink 잡 | — | 5 미만이면 빨강(정상 5잡) |
| 적재 지연 | `s` | 60초 = 늦은 이벤트 가드 기준(docs/20) |

**임계를 알럿 임계와 똑같이 맞춘 이유**: 화면의 빨강과 Slack 알림이 다른 기준이면 둘 중 하나를 믿지 않게 된다.

### 6-2. 두 번째 원인 — 첫 화면이 너무 길었다
관측 대시보드가 **패널 25개 · 세로 70 그리드**였다. 스타일을 고쳐도 한 화면에 다 쏟아지면 여전히 난잡하다.

사용자: "대시보드를 더 쪼갤래? 그건 너무 개수가 많아지나?"
→ **쪼개지 않고 접었다.** 문제는 개수가 아니라 **한 번에 보이는 양**이었다.
대시보드를 늘리면 "어느 대시보드였더라"가 새 비용으로 생긴다.

| | 전 | 후 |
|---|---|---|
| 관측 첫 화면 | 패널 25 · 높이 70 | **패널 8 · 높이 14** |
| 이상탐지 첫 화면 | 패널 18 | **패널 7** |
| 대시보드 수 | 2 | **2 (유지)** |

펼쳐 두는 것은 **"지금 정상인가"에 답하는 두 섹션**뿐이다(지금 상태 · 유입 / 지정 상태 · 전이).
나머지는 접힌 제목으로 남아, 이상이 보일 때 펼친다.

### 6-3. 배치도 손봤다

## 7. 시각화 종류와 문구 정리 (2026-09-20 15:10 ~ 15:25 UTC)

> 사용자: "각 섹션에 맞게 알맞은 그래프를 넣어야 하지 않을까? 지금은 그런 느낌이 아니야."
> 그리고 "이상탐지 보드의 현재가는 뭐야?", "하이픈(—) 표시는 AI 티가 난다".

### 7-1. 적용한 원칙
어떤 그래프를 쓸지는 **그 패널이 답하는 질문의 모양**으로 정한다.

| 질문 | 시각화 |
|---|---|
| 지금 값 하나가 정상인가 | stat, 배경색으로 정상/위험 |
| 시간에 따라 어떻게 변했나 (연속) | 선 그래프 |
| 날짜별로 몇 건인가 (이산) | 막대 그래프 |
| 항목끼리 크기 비교 | 가로 막대 |
| 개별 사건을 하나씩 본다 | 표 |

**바꾼 것**

| 패널 | 전 | 후 | 이유 |
|---|---|---|---|
| 업비트·바이낸스 대조 일치율 | 선 그래프 | **stat + 30일 스파크라인** | 값이 늘 100 이라 선이 평평하다. "지금 몇 %인가"가 질문이므로 큰 숫자 + 추세가 맞다 |
| 대조가 어긋난 셀 수 | 선 그래프 | **막대** | 날짜별 건수는 이산값이다 |
| 늦게 도착한 행과 복구한 행 | 선 그래프 | **막대** | 같은 이유 |
| 7일간 단계별 사건 수 | 표 | **가로 막대** | 단계끼리 크기를 비교하는 질문이다 |
| 분당 들어온 행 수 | 막대(선형 축) | **선 + 로그 축** | 경로별 유입이 10배 넘게 차이나서 선형 축이면 바이낸스 체결이 나머지를 눌러 안 보인다 |

### 7-2. "현재가" 가 무엇이었나
`mart_daily_summary` 의 **가장 최근 KST 하루 종가**였다. 실시간 가격이 아니다.
그런데 **① 지금 경보가 걸린 상태** 섹션에 있어서, 경보 지표들 사이에 가격 하나가 끼어 있는 꼴이었다.

→ **④ 선택한 종목 살펴보기** 로 옮기고 이름을 **`선택 종목 최근 종가`** 로 바꿨다.
그 섹션의 다른 지표(전일 대비·거래량 변동·매수 비율·일중 변동폭)가 전부 '선택한 종목의 최근 하루'를 말하므로 거기가 제자리다.
설명에도 "실시간 가격이 아니다, 실시간은 ② 의 가격 차트에서 본다"를 적었다.

### 7-3. 문구를 사람 말로
제목에서 **`—`(엠대시)를 전부 없애고**, 영어·약어·내부 용어를 풀었다.

| 전 | 후 |
|---|---|
| `① 지금 상태` | `① 지금 정상인가` |
| `③ 지연 — 어디서 밀리나` | `③ 어디서 밀리나` |
| `④ 정확성 — 거래소·원장과 대조` | `④ 값이 맞나 (거래소·원장 대조)` |
| `호스트 load1 (코어 4)` | `서버 부하 (코어 4개)` |
| `Flink 소스 busy max (ms/s)` | `Flink 소스 포화도` |
| `Upbit e2e p95 (초)` | `업비트 지연 p95` |
| `Markets Tracked (모니터링 마켓)` | `감시 중인 마켓 수` |
| `⚠ 이상탐지 지정 전이 (최근 1시간)` | `최근 1시간 새 경보` |
