# 38. 대시보드 정비 — 공개 데모가 되자 드러난 것들 (2026-09-20 10:45 ~ 11:15 UTC)

> 사용자: "이 관점에서 이 대시보드도 손봐야 하는 거 아니야? 결국 알려주고 싶은 내용이 좀 바뀐 거잖아. airflow 도 전이랑 많이 바뀐 걸로 아는데."
> 맞다. 그리고 확인해 보니 **보여주는 내용이 바뀐 것보다 먼저, 깨진 것이 있었다.**

## 1. 전수 점검 결과 — 50개 쿼리 중 13개가 깨져 있었다

### 1-1. 왜 놓쳤나 — grep 은 Grafana DB 안을 못 본다
docs/34 #3(시간 규약 통일)에서 `trade_date → day_kst`, `hour_start → hour_kst` 로 바꾸면서
"소비자"를 **저장소 안에서 grep** 으로 찾았다. 프로비저닝 JSON 3개(`grafana/provisioning/dashboards/json/`)는
그렇게 잡혔지만, **UI 로 만든 대시보드는 Grafana 의 DB 에만 있어서 grep 에 안 걸렸다.**
그 결과 `cdc-dbt-analytics` 10패널이 아침부터 `Missing columns: 'trade_date'` 로 죽어 있었다.

→ 교훈: **열 이름을 바꿀 때 소비자 목록은 저장소가 아니라 "그 열을 읽는 모든 주체"** 다.
Grafana DB, cron 스크립트, n8n 정의처럼 저장소 밖에 사는 소비자가 있다.

### 1-2. Prometheus 12패널 — 만든 것과 도는 것
`airflow-operations` 는 Prometheus 12패널이었는데, Prometheus 는 docs/34 #1 에서 `ops` 프로필로 내려
평소엔 꺼져 있다. **대시보드가 통째로 빈 화면**이었다.
대체재(`ops_metrics_5m`, 5분 cron 호스트 지표)는 docs/32 에서 이미 만들어 뒀는데 대시보드만 안 옮겼다.
오늘만 네 번째 같은 유형이다(잠든 DAG 4개 · 옛 JAR 배포 · 실행된 적 없는 방화벽 스크립트 · 이것).

## 3. 대시보드를 만들다 잡은 진짜 버그 — 3자 대조가 열린 날에 항상 틀렸다
품질 패널을 붙이자마자 **오늘치 원장 3자 대조가 5심볼 전부 불일치**로 떴다(어제는 0).
실제 데이터를 세어 보니 MySQL 479 = ClickHouse 479 로 **멀쩡했다.**

원인: 비교하는 두 값의 **측정 시각이 달랐다.**
- `my_*`(MySQL·거래소) = 생성기가 매시 남긴 스냅샷 → 그 시각까지의 값
- `ch_*`(ClickHouse) = dbt 실행 시점의 **현재** 값

그 사이에 낸 주문 9건/심볼이 통째로 차이로 잡혔다. 즉 **열린 날은 구조적으로 항상 불일치**였다.
(`quality_alerts` 는 `day_utc < today()` 라 거짓 알럿은 안 났지만, 대시보드에는 그대로 보였다.)

고침 — 자르는 기준이 열마다 다르다는 것이 핵심이었다:

| 열 | 기준 |
|---|---|
| 주문 수 | `created_ms ≤ 마지막 대조 시각` (MySQL 도 '생성'을 센다) |
| 상태 집계(체결·취소·수량) | `updated_ms ≤ 마지막 대조 시각` |
| 체결 수 | `filled_ms ≤ 마지막 대조 시각` |

1차로 주문 수만 맞췄더니 5 → 2 로 줄었고, 남은 2건은 **기준시각 전에 생겼지만 그 뒤에 체결된 주문**이었다
(BTC·SOL 각 1건). 상태 집계까지 같은 시각으로 자르니 **0**.

## 5. 재편 — "어떻게 만들었나"가 아니라 "무엇에 답하나"로 (11:15 ~ 11:40 UTC)

> 사용자: "파이프라인 관측 및 오류 탐지용 1개, 이상탐지 1개 이렇게 각각 만드는 건 어때? … 근데 전자랑 airflow 랑 겹치나?"
> **겹쳤다.** 그리고 그게 원래 구조의 문제였다.

### 5-1. 겹침을 세어 봤다
대시보드가 **만들어진 경위**(원본 / dbt / 운영)로 나뉘어 있어, 같은 주제가 여러 곳에 흩어져 있었다.

| 주제 | 어디에 있었나 |
|---|---|
| 유입 | 메인 2패널 + 운영 1패널 |
| 지연 | 메인 2 + 품질 1 + 운영 3 |
| 이상탐지 산출물 | 메인 2 + 품질 1 + DBT 3 + 운영 1 |
| 시장 데이터 | 메인 4 + DBT 10 |

보는 사람은 만들어진 경위를 모른다. **"지금 파이프라인이 멀쩡한가"와 "시장에 뭐가 터졌나"** 두 질문으로 찾는다.

### 5-2. 두 개로
| 대시보드 | 답하는 질문 | 구성 |
|---|---|---|
| **파이프라인 관측 · 오류 탐지** (23패널) | 지금 제대로 도는가 | ①지금 상태 ②유입(두 거래소 네 경로) ③지연(종단·적재·CDC 구간) ④정확성(Upbit·Binance·원장 3자) ⑤오류·공백(늦은 행·수리 계보·공백 라벨·토픽 계약) ⑥자원·알럿 |
| **이상탐지 (시장 경보)** (18패널) | 무엇이 언제 지정됐고 그 판정이 맞나 | ①지금 지정 상태 ②전이 ③규칙 평가(정밀도·재현율·선행) ④거래대금 급등 ⑤마켓 상태 + 시장 맥락 |

읽는 순서를 섹션 번호로 박았다. ③지연을 종단·적재·CDC 구간 셋으로 나눈 이유는
**구간을 나눠야 병목이 어디인지 말할 수 있기** 때문이다(docs/08 적재 지연 36.9시간 사고의 교훈).

**패널은 옮긴 것이지 다시 쓴 것이 아니다.** 이미 검증한 SQL 을 그대로 들고 자리만 새로 줬다 —
재작성하면 오타로 새 버그가 생긴다. 내려간 정의 3개는 `grafana/archive/` 에 이유와 함께 보관했다.

방문자에게 보이는 대시보드는 정확히 이 2개다(다른 프로젝트 2개는 대시보드 단위 권한으로 가림).
