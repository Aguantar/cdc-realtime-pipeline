# 37. 계약 검증 상시화 · 거래소 공지 라벨링 (2026-09-20 07:45 ~ 08:05 UTC)

> 사용자: "검증기 cron이랑 점검 공지 라벨링도 해줘."
> 둘 다 docs/34 #8 과 docs/33 이 **한계로 남겨 둔 것**이다. 만들어 두고 안 도는 것은 없는 것과 같다 —
> 같은 날 DAG 4개가 그렇게 잠들어 있던 것을 발견했다(docs/22 §6 ③).

## 1. 토픽 계약 검증을 상시로

### 왜 Airflow 가 직접 안 돌리나
검증기는 Kafka CLI(`docker exec`)가 필요하다. 그런데 `health_check` 부터 모든 DAG 은
**"네트워크 API 기반, Docker 소켓 불필요"** 를 지키고 있다(docs/20). 소켓을 Airflow 에 주면 그 원칙이 깨진다.
→ **호스트 cron 이 매시 검증하고 결과를 표에 적는다. 판정·발송은 Airflow 가 그 표를 보고 한다.**
알림은 한 경로로만 나가야 하고(docs/32), 그 경로는 Airflow 다.

| | |
|---|---|
| 표 | `cdc_pipeline.schema_validation_runs` (ran_at·topic·status·checked·violations·detail, TTL 90일) |
| 수집 | `validate-topic-schemas.py --record`, cron 매시 25분 |
| 판정 | `quality_alerts` 규칙 **Topic Schema** 추가(매시 :50) |

### 두 가지를 본다 — 그리고 두 번째가 더 중요하다
1. 마지막 실행에 위반이 있나 (`bad_topics > 0`)
2. **검증기가 아직 도나** (`stale_min > 180`)

②가 없으면 검증기가 죽었을 때 위반이 0 으로 보인다. **"위반 없음"과 "검사 안 함"은 다르다.**
임계 180분은 매시 cron 이 한 번 걸러도 울리지 않는 여유다.

### 검증
- 규칙 SQL 첫 실행이 **500** 이었다. 원인: `sum(violations) AS violations` 로 두니 `argMax(detail, violations)` 가
  "집계 안의 집계"가 됐다 — ClickHouse 의 **SELECT 별칭이 같은 이름의 원본 열을 가리는** 함정이고,
  docs/34 #3 에서 WHERE 로 겪은 것과 같은 종류다. 별칭을 `violation_count` 로 바꿔 해결.
- 평소엔 위반이 0 이라 이 판정식은 '통과'만 한다. **통과만 하는 판정은 없느니만 못하므로** 단위 테스트로
  증명했다(6케이스): 정상이면 안 울림, 위반이면 울리고 메시지에 깨진 필드가 들어감, 멈추면 울림,
  경계 180분은 정상·181분은 위반. DAG 테스트 15/15.
- `quality_alerts` 실행: checked 4 → **5**, fired 0.

## 2. 거래소 공지로 수집 공백 라벨링

### 먼저 확인한 것 — 카테고리를 믿으면 틀린다
공지 **1,200건**(2025-06-24 ~ 2026-09-19)을 받아 실제로 세어 봤다.

| 분류 | 건수 | 거래가 멈추나 |
|---|---|---|
| `category='점검'` | 5 (표본 150 중) | **대부분 아니다** — 신분증 진위확인·원화 입출금이다 |
| 제목 `^서버 점검 안내` | **3** | **그렇다.** 본문: "점검 시간 내 업비트 서비스 전체 이용이 제한", KRW·BTC·USDT 전 마켓 |
| 제목 `… 거래 지원 일시 중단` | **5** | 그 코인만. 리브랜딩·토큰 스왑 |
| 입출금 관련 | 404 | 아니다 — 거래는 계속된다 |

**카테고리로 걸렀다면 거래 중단 8건을 놓치고 멀쩡한 시간을 점검으로 오인했을 것이다.**
그래서 분류는 카테고리가 아니라 제목·본문으로 한다.

### 창은 지어내지 않는다
'서버 점검 안내' 본문에는 시각이 `2026-07-06(월) 02:00` 형태로 여러 번 나오는데
**최소가 점검 시작, 최대가 거래 재개**다(3건 전부 확인). KST 이므로 9시간을 뺀다.

| 게시 | 창(UTC) | 길이 |
|---|---|---|
| 2025-10-26 | 17:00 ~ 23:55 | 415분 |
| 2026-04-13 | 17:00 ~ 22:30 | 330분 |
| 2026-07-06 | 17:00 ~ 21:40 | 280분 |

코인별 중단은 본문에 **재개 시각만** 있는 경우가 있어 창을 만들지 않았다. 대신 게시 시각이 공백 ±24시간
안이면 **후보로만** 올린다. 지어낸 창으로 '설명됨' 도장을 찍느니 후보를 주고 사람이 닫는 편이 낫다.

### 만든 것
| 것 | 내용 |
|---|---|
| `clickhouse/exchange_notices.sql` | 공지 원문 보관(RMT). **공지는 사후 갱신된다** — "거래 재개 시점 안내"가 같은 글에 덧붙으므로 최신본만 남긴다 |
| `scripts/labels/poll_exchange_notices.py` | 매시 cron(35분). 증분이되 **최근 15건은 이미 가졌어도 다시 받는다**(갱신을 놓치면 재개 시각을 영영 모른다). 최초 1,200건 5분 12초, 증분 4.5초 |
| `dim_exchange_notices` | scope(exchange_wide / market / deposit_withdrawal / other) + 티커 + 창 |
| `dq_ingest_gaps_labeled` | 공백 × 공지. 전체 점검은 **구간 겹침**으로 확정, 코인별은 후보 |
| 주간 다이제스트 ⑦ | 공백 건수·설명된 수·**설명 없고 60초 이상** |

**구현 메모**: ClickHouse 는 JOIN ON 에 범위 조건을 못 쓴다(code 403). 거래를 멈추는 공지가 15개월에 8건뿐이라
배열 한 줄로 만들어 CROSS JOIN 뒤 `arrayFilter` 로 겹침을 본다 — 조인보다 싸고 읽기 쉽다.

### 검증
- **겹침 로직**을 가상 공백 4개로 확인(쓰기 없음): 점검 한복판 ○, 시작에 걸침 ○, 끝난 뒤 ✗, 점검 없는 날 ✗.
  실제 데이터로는 우리 공백 8건이 전부 2026-09-16 이후라 점검과 겹치는 것이 없다 — **기계는 증명됐고
  적용 사례는 아직 없다**. 다음 서버 점검 때 자동으로 라벨이 붙는다.
- 다이제스트 기준을 **60초 이상**으로 둔 이유: 공백 8건 중 6건이 재기동(startup)이 만든 수 초짜리이고
  전부 자동으로 메워졌다. 그것까지 매주 올리면 '고칠 것'이 늘 차 있어 아무도 안 본다.
  60초는 늦은 이벤트 가드·커버리지 판정과 같은 '실시간 아님' 기준(docs/20). 적용 결과 3건이 남는다
  (3600s manual = 재처리, 511s·84s startup = 재배포).
- `dbt build` **111 PASS / 0 ERROR**, DAG 테스트 15/15.

## 3. 한계
- 코인별 거래지원 중단은 **후보만** 준다. 본문 형식이 일정하지 않아 창 파싱을 믿을 수 없다.
- 공지 수집은 15개월치(1,200건)에서 멈췄다. 그 이전은 필요해지면 `--full` 의 `MAX_PAGES` 를 늘린다.
- 라벨은 `ingest_repairs`(우리가 메운 공백)에만 붙는다. 호가 공백(`dq_orderbook_gaps_daily`)에는 아직 안 붙였다.
- 검증기 cron 은 호스트에 있다 — 호스트 cron 이 죽으면 Airflow 의 staleness 규칙이 그것을 알린다(①이 아니라 ②가 잡는다).
