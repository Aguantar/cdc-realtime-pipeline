# 07. 중복 적재 감사 (Dedup Audit)

- 실행일: 2026-09-06
- 대상: `cdc_pipeline.crypto_trades` 91,061,136행 (감사 시점 기준)
- 방법: 읽기 전용 쿼리. 신규 생성한 `readonly_user` 계정(readonly=2, SELECT 전용)으로 실행하여 계정 검증을 겸함.
- 배경: 파이프라인 전 구간이 at-least-once 구성. Connect 프로듀서 `enable.idempotence=false`, Flink JDBC sink 비트랜잭셔널, ClickHouse MergeTree(dedup 없음).

## 2. 유입 경로 분석

### 2-1. 2026-02 대량 중복 = 46시간 장애 복구 재소비

일 단위 분포(2월, source_ts 기준):

| 날짜 | 중복 행 |
|---|---|
| 02-13 | 49,878 |
| 02-18 | 5 |
| 02-19 | 846,320 |
| 02-20 | 664,968 |
| 02-21 | 78,887 |
| 02-23 | 1,026 |
| 02-27 | 140 |

샘플 검증(trade_id=5285572, 8중복):

```
source_ts  2026-02-21 04:00:00.992  (8행 모두 동일)
cdc_ts     2026-02-21 04:00:00.997  (8행 모두 동일 — Debezium 캡처는 1회뿐)
flink_ts   02-21 04:00:01 / 04:00:15 / 04:00:25 / 04:00:35
           02-23 02:30:04 / 02:30:28 / 02:30:53 / 02:31:19
```

- cdc_ts가 동일하므로 프로듀서(Debezium/Connect) 재시도 유입이 아님.
- flink_ts 앞 4개는 02-21 04:00 장애 시각의 원본 1회 + restart 시도 3회(약 10초 간격)와 일치. 06-phase6-record.md의 "restart 3회 실패 → FAILED" 타임라인과 정확히 대응.
- flink_ts 뒤 4개는 02-23 02:21 장애 발견 직후 복구 기동(02:30~02:31, 약 25초 간격 4회)과 대응. 컨테이너 기동 시각(02-23 11:25 KST = 02:25 UTC 부근)과도 일치.
- 02-19와 02-20에 중복이 가장 많은 이유: 복구 시 Kafka에 남아 있던 retention 구간(retention.hours=72)을 앞에서부터 재소비. 02-19~02-21 04:00 데이터는 장애 전에 이미 적재돼 있었으므로 재소비분이 전부 중복이 됨. 장애 공백 구간(02-21 04:00~02-23 02:21)은 원본 적재가 없어 중복도 없음 — 공백 복구와 중복 유입이 동전의 양면이었음.
- 02-13의 49,878건은 장애 이전 개발 단계의 별건. cdc_ts까지 동일한 쌍이 관찰되어 sink 재시도 또는 잡 재실행으로 추정. 규모가 작고 시기가 오래되어 추가 추적은 생략.

### 2-2. 2026-03 이후 소규모 중복 = JDBC sink 배치 재시도

- 발생일이 산발적(월 1~3일)이고 건당 규모가 배치 크기(200행) 미만.
- 최근 30일 Flink 체크포인트 복구 이력 0회, 컨테이너는 02-23 이후 206일 무중단. 즉 잡 재시작으로 인한 중복이 아님.
- 09-06 당일 샘플(trade_id=95075615 등 13건): cdc_ts 동일, flink_ts가 127ms 간격 — 동일 배치가 짧은 간격으로 2회 쓰임. JdbcSink 재시도(MAX_RETRIES=3, 비트랜잭셔널) 경로로 확정.
- 참고: 09-06 발생분은 본 감사의 uniqExact 쿼리가 유발한 메모리 압박 시간대(12:03)와 겹침. INSERT가 일시 실패하면 sink가 배치를 통째로 재전송한다는 실증 사례.

### 2-3. 부수 발견: trade_id 재사용

trade_id=2가 서로 다른 두 실제 이벤트(02-13, 02-21)로 존재. MySQL cleanup 과정에서 auto_increment가 리셋된 것으로 보임.

- 의미: trade_id 단독은 글로벌 유니크 키가 아님. dedup 키는 (source_ts, trade_id) 조합이어야 함.
- 현재 ORDER BY (market, source_ts, trade_id)가 이미 이 조합을 포함. ReplacingMergeTree로 전환할 경우 키 변경 없이 성립하며, 재사용된 trade_id(서로 다른 source_ts)를 잘못 합치지 않고 재전송 중복(동일 source_ts)만 제거함.

## 3. 결론

1. 실측 중복 1,641,600건(1.80%). 단일 원인이 지배적 — 46시간 장애 복구 시 Kafka retention 구간 재소비(약 1.59M건).
2. 정상 운영 중에도 sink 재시도로 월 수십 건 수준의 중복이 계속 유입되고 있음(6개월 누적 373건, 오늘도 13건 발생). at-least-once 구성의 실제 비용이 측정됨.
3. 프로듀서 경로(idempotence=false)로 인한 중복은 이번 감사에서 관측되지 않음. 다만 관측되지 않았을 뿐 보장이 없는 상태이므로 Phase 2(idempotent producer)는 여전히 유효.
4. 집계 영향: trade_aggregations와 dbt 마트는 crypto_trades를 원본으로 하므로 2026-02 지표는 중복만큼 과대집계돼 있음. 2월 데이터를 분석에 쓸 경우 dedup 서브쿼리 필요.

## 4. 후속 조치

- **Phase 2 — 적용 완료 (2026-09-06)**: Connect 워커에 `CONNECT_PRODUCER_ENABLE_IDEMPOTENCE: "true"` 추가 후 kafka-connect만 재기동. 검증 3종 통과 — 워커 설정 파일에 `producer.enable.idempotence=true` 반영, 커넥터 태스크 프로듀서 2개(connector-producer-mysql-cdc-connector-0, connector-producer-postgres-circuit-connect-0) 시작 로그에 `enable.idempotence = true`, 재기동 후 유입 정상(3분간 452건). 한계: 단일 프로듀서 세션 내 재시도 중복만 방어. Connect 재시작 후 오프셋 되감김 재전송은 방어 불가 — Phase 3-A 감시가 보완. 내부 스토리지 토픽 프로듀서에는 워커 `producer.` 오버라이드가 적용되지 않아 로그에 false로 남는데 정상임(중복 유입 경로 아님).
- **Phase 3-A — 적용 완료 (2026-09-06)**: daily_pipeline의 check_duplicates를 당일 (source_ts, trade_id) 중복 검사로 교체(메모리 캡 500MB). 중복 > 0이면 quality gate에 DEDUP FAIL 항목 추가, Slack 일일 리포트에 건수 표기(0건이면 "중복 0건" 라인). 의존성은 check_duplicates >> quality_gate로 변경. 당일 수동 실행으로 검증 — 실제 중복 13건을 게이트가 감지해 4/6(66.7%) FAIL 처리, Slack 발송까지 성공. FAIL 대응 절차는 DAG docstring에 기록(소량 간헐 FAIL은 sink 재시도 유입으로 정상, 배치 크기 200건 이상 반복 시 조사).
- **Phase 3-B — 연기 (코테 이후)**: ReplacingMergeTree(cdc_ts) 전환. 키는 현행 유지 가능(2-3 참조). 91M 재작성은 파티션 분할 필수, 조회부(FINAL/argMax) 영향 검토 필요. 2026-02 파티션 dedup 백필과 마트 재계산도 이때 함께.
- **수치 표기 정리 — 완료 (2026-09-06)**: README 총 적재를 "누적 91.06M행, 고유 89.42M" 형식으로 갱신, 정합성 행의 "중복 0.006% 이하" 표기를 실측값으로 교체, stg_trades 모델 description에 2026-02 과대집계 주석 추가.
