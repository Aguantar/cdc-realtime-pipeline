# 포트폴리오 — DE 로서 어필되는 지점 (2026-09-18 기준, 지금까지의 여정만)

이 문서는 "무엇을 만들었나"가 아니라 **"무엇을 재서 무엇을 결정했나"** 를 모은다. 모든 숫자는 측정 조건과 출처 문서를 붙였다. 앞으로 할 일은 여기 없다(docs/19 §2·docs/24 §6).
대상 파이프라인: Upbit WebSocket(287 KRW 마켓 체결 + 호가) → producer → MySQL → Debezium → Kafka → Flink → ClickHouse, Airflow·dbt·Grafana, 4코어 미니 PC 1대에 26컨테이너.

## 2. 지연 — 어디서 나는 지연인지 층을 나눠 잰다
| 어필 포인트 | 실측 | 왜 | 출처 |
|---|---|---|---|
| 8월 적재 지연 사고 | 최대 36.9시간 지연. 원인 producer 상한 포화. 기존 체크는 적재 이후 구간만 봐서 감지 못함 → source_ts − upbit_ts 기준 체크 신설 | 지연은 "거래소 시각 − 적재 시각"으로 재야 사고가 보인다 | docs/08 |
| e2e p95 가 무엇에 결정되는지 | 체결 e2e p95 4.7s = producer 배치 2s + JDBC 배치 3s. 유입이 많은 09시(59 rows/s)가 p95 가 가장 낮고(2.05s), 새벽이 가장 높다(2.3~2.4s) | 배치 창을 행이 빨리 채우기 때문. 자원 부족이 아니다 — "지연이 낮다 = 여유"도 틀린 직관 | docs/14 §2, docs/23 §4 |
| 늦은 이벤트 가드 | 백필 1건이 오탐 2건(3회 재현). 단조 순서 가드는 재정렬 5.87%/최대 4.8초 실측으로 기각 → 적재 지연 > 60초 제외 | 임계 60초는 정상(7.75s)의 8배이고 이미 쓰는 "실시간 아님" 기준 | docs/17 §4-4, docs/20 §1 |
| 정체 판정 지표 | Flink 컨슈머 lag 은 체크포인트 커밋 톱니(rate×60)라 적체가 아니다 → "발행 − 적재"로 | 대시보드 함정을 실측으로 확인 | docs/18, docs/23 §1 |
