관찰(docs/14) 뒤 첫 구조 작업. 원칙: **현업 관행이거나, 아니면 "왜"를 한 문장으로 답할 수 있는 선택만 한다.**

## 2. 구성

```
reconcile_trades (06:35 UTC, catchup=False, backfill 가능)
  fetch_hourly_candles  [pool upbit_rest]  거래소 KRW 마켓 목록 → 시간봉 24개/마켓 → upbit_hourly_candles
  → dbt_build_reconcile  dbt build --select +int_reconcile_hourly --vars reconcile_date=ds
       모델 int_reconcile_hourly: 마켓×시간 ch_vol / candle_vol (체결시각 기준, FINAL)
       테스트 assert_reconcile_no_loss(ratio<99), assert_reconcile_coverage(ch_n=0), not_null
  → summarize [all_done]  가중 비율·셀·최악 10개 → 실패면 Slack + 태스크 실패
```
dbt 추가: `reference` 소스(시간봉·일봉·경보 이력), `crypto_trades` freshness(15분 warn / 60분 error), `assert_trades_unique_market_seq`.
daily_pipeline 변경: `dbt_source_freshness` 선행, KST 체결시각 하루 경계, `schedule` 파라미터.

**발견 1 — 구독 누락 (커버리지 테스트가 잡음).** KRW-BFC 는 09-10 상장. producer·수집기는 09-09 기동 시 마켓 목록을 한 번만 받아 이후 상장 마켓을 구독하지 않는다. 체결 0건, 호가 0건, 6일째. 관찰 기간 cron 대조는 마켓 목록을 ClickHouse 에서 가져와 **구조적으로 볼 수 없었다**(6일 연속 "100.0%" 는 이 마켓을 제외한 값). docs/14 튜닝 5번(마켓 목록 갱신)이 실제 손실로 확인됨. 업비트 REST 체결 이력은 7일이라 BFC 백필 가능 기한은 09-17 까지.

**발견 2 — 재연결 구멍 (유실 테스트가 잡음).** 09-15 20:47:00 UTC producer WebSocket 끊김 → 20:47:05 재연결. 그 5초 사이 체결이 빠졌다. TIA 20시 셀 50.6%: REST 틱 대조로 20:47:02 체결 2건(2,280 + 20 TIA) 누락 확인. 같은 시간대 8마켓 셀이 89~97%. 일 단위로는 99.27% 이상이라 종전 가중 비율만 보면 넘어갔을 크기. 관찰 기간 producer WARNING 1건(docs/14 미조사 항목)의 정체가 이것.

## 4. 조치 결과 (같은 날 실행)

### 4-1. BFC 백필 — 완료
REST 원장 261,713건 전부가 누락(MySQL 0건)이었고 전량 복구했다. 소요 462초, ClickHouse 도착 확인 11:06:57.
백필 중 다른 마켓 적재 지연 p50 1.2초로 실시간 영향 없음. 상장 시각이 09-10 04:00 UTC 라 REST 7일 창 안이었다.
부산물로 BFC 알림 138건이 오늘 날짜로 생성됨 → CSV 보존 후 삭제(`~/pipeline-observation/removed_alerts_bfc_backfill_20260916.csv`).
09-10 백필 때와 성격이 다르다. 그때는 7일 전 가격과 현재가를 비교한 **무효 비교**였고, 이번은 단일 마켓을 시간순으로 넣어
연속 체결 비교 자체는 유효하다. 문제는 `detected_at` 이 오늘이라 알림 집계의 날짜 축이 틀어지는 것뿐이다.

### 4-2. 마켓 목록 주기 갱신 — 구현·배포
09-10 worklog 에 "관찰 뒤 항목"으로 적어 둔 것을 구현했다. 핵심은 **재연결 없이 갱신**하는 것이다.

먼저 검증부터 했다. 기록에는 "업비트는 최신 구독 메시지로 교체"라고 적혀 있었지만 실측한 적이 없었다.
별도 연결로 프로브를 돌려 1마켓 → 3마켓(확장) → 1마켓(축소)을 보냈고, 세 번 모두 구독이 교체되며 연결이 유지됐다.
따라서 목록 갱신이 수신 공백을 만들지 않는다.

| 항목 | 값 | 왜 |
|---|---|---|
| 주기 | `MARKET_REFRESH_SEC=300` | 상장은 공지 후 예고되므로 분 단위 정밀도가 필요 없다. REST 한도 10/s 대비 5분당 1회는 무시할 수준 |
| 방식 | 같은 연결에서 구독 메시지 재전송 | 재연결하면 그 사이가 공백이 된다(= 4-3 이 바로 그 손실) |
| 실패 처리 | 조회 실패·100개 미만 응답이면 기존 목록 유지 | 업비트 장애 시 구독이 축소되는 것이 가장 위험 |
| 예외 | `MARKETS` 를 명시하면 갱신 안 함 | 사용자가 목록을 고정한 것은 의도이므로 존중 |
| 로그 | 변경 시 추가·제외 마켓을 WARNING, 10개 초과는 축약 | 조용한 변경은 나중에 원인 추적이 불가능하다 |

코드 경로 검증: 가짜 writer(MySQL 미사용)로 `subscribe_upbit` 을 2마켓·갱신 10초로 구동 → 갱신 시점에 287마켓으로 확장,
수신 마켓 수 3 → 43 으로 증가 확인. 배포 후 실측: 11:22:46 BFC 체결이 `sequential_id` 17895577664810000 으로 거래소 원장과 일치.

배포 공백(체결): producer 11:20:49.1 → 11:20:51(2초), collector 11:21:00.2 → 11:21:01.6(1.4초). 백필 대상에 포함.

### 4-3. 재연결 구멍 백필
09-15 20:46:45~20:47:30(45초) 287마켓 대조: REST 996건 / MySQL 836건 / **누락 160건(16.06%)**.
5초 재연결이 45초 창의 16%를 날린 것이 수치로 확인됐다.

### 4-4. 백필이 스트림 상태를 오염시킨다 (새로 확인)
20:47 구간 백필(160행) 직후 알림 10건이 났는데, 체결 시각으로 갈라 보니 정확히 두 묶음이었다.

| 묶음 | 예 (KRW-LIT) | 내용 |
|---|---|---|
| 백필된 옛 체결 5건 | 11:31 탐지, 체결 09-15 20:47:01, "급락 5,915 → 5,515 (6.76%)" | 6일 전 체결가를 **현재가**와 비교 |
| 직후 실시간 체결 5건 | 11:33 탐지, 체결 09-16 11:33:24, "급등 5,515 → 5,910 (7.16%)" | 실시간 체결이 **백필된 옛 가격**과 비교되어 되튐 |

원인은 `AnomalyDetector` 가 마켓별 `lastPrice` 를 keyed state 로 들고 직전 체결과 비교하기 때문이다.
백필 행이 같은 Kafka 토픽으로 실시간 스트림에 끼어들면 그 상태가 과거 값으로 덮이고, 다음 실시간 체결이 그 값과 비교된다.
**한 번의 백필이 두 번 오탐을 만든다.** 09-10 백필의 1,687건도 같은 기전이었다(그때는 기전을 특정하지 못하고 "7일 전 가격 비교"로만 적었다).

BFC 백필 138건에서는 이 되튐이 안 보였다. BFC 는 애초에 구독이 안 돼 실시간 체결이 없었으므로 끼어들 스트림 자체가 없었다.
즉 **구독 중인 마켓을 백필할 때만** 발생한다.

10건은 CSV 보존 후 삭제(`removed_alerts_gap_backfill_20260916.csv`). 이 사실은 아래 gap-fill 설계의 전제가 된다.

## 5. 남은 것
1. **재연결 gap-fill**: 재연결 직후 REST 로 끊긴 구간을 자동으로 메우는 로직. 재연결은 주 2회꼴이고(docs/14 H4)
   이번에 45초 창의 16%가 날아간 것이 확인됐으므로 자동화가 맞다. 다만 §4-4 때문에 **그냥 넣으면 안 된다** —
   메울 때마다 이상탐지 상태가 오염되어 알림이 두 배로 튄다. 선택지:
   (a) 체결 이벤트에 `is_backfill` 플래그를 실어 `AnomalyDetector` 가 상태 갱신만 하고 알림은 내지 않게,
   (b) 이벤트 시각이 처리 시각보다 N분 이상 늦으면 알림 생략(늦은 이벤트 일반 처리),
   (c) 백필을 별도 토픽·별도 잡으로 분리.
   (b) 가 가장 단순하고 gap-fill 뿐 아니라 모든 지연 유입에 적용된다. 코드 변경 — 사용자 결정 대기.
2. `markets` 상태 테이블(상장일·폐지일·경보) — 마켓 마스터. CDC 를 쓸 자리이기도 하다(docs/16 §CDC 유의미화).
