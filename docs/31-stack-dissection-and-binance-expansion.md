# 31. 스택 해체 분석과 Binance 실시간 확장 (2026-09-20)

> 사용자: "각 스택이 진짜 제대로 일하는지 꼼꼼히 해체 분석하고 build 시작. 분산 처리의 의미가 다시 살아나야 하나?"
> 원칙: 수치는 전부 실측(09-20 00:10~00:40 UTC, 일요일 오전 KST — 한 주 중 가장 조용한 시간대라 하한으로 읽는다).

**해체의 결론**: 정확성 장치(Debezium 두 모드·RMT·대조·동등성)는 볼륨과 무관하게 일하고 있다. 볼륨으로 일하는 것은 호가 경로뿐이고, Kafka 상한의 1%, Flink 슬롯의 1/4, ClickHouse 쓰기의 극히 일부만 쓰고 있다. "Flink 가 의미 있는 파이프라인"이라는 처음 목표에 비추면 **체결 경로의 볼륨이 빈 자리**다.

## 2. 분산 처리의 의미는 다시 살아나야 하나
- **아니다, 그러나 병렬·파티셔닝 설계는 살아난다.** Binance 를 붙여도 총 유입은 ~1,000 events/s 다. 코어 4개 미니PC 하나에서 브로커·TM 을 늘리는 건 여전히 형식이다(docs/24 결론 유지).
- 대신 처음으로 **파티션 수 = 병렬도 = 키 분포**를 설계해야 한다: 체결 토픽 6 파티션(키=symbol, 683 심볼이 6개에 해시 분포), Flink 소스 병렬 3(슬롯 4→6), 싱크 배치 1,000/3s(docs/23 의 병목 근거). 호가 재구성(2단계)은 심볼별 키 상태(호가장)라 keyBy 가 실제 의미를 가진다.
- 분산이 필요해지는 지점은 docs/23 그대로: 5,000/s 부터 소스 체인 busy 1.0 → 그때 순서는 파티션 → 병렬도 → 그 다음이 브로커·TM 추가.

|---|---|---|

| 감시 | health_check: Flink 잡 4, binance 적재 60초 0 알림 | — |

### 3-3. 2단계 — 호가장 재구성 (1단계 24시간 관찰 뒤)
- 상위 50 심볼 `depth@100ms` → Flink keyed state(심볼별 호가장 맵): REST 스냅샷 + `U/u` 순번 검증 + 수량 0 삭제. 순번 끊김 → 재스냅샷(카운터). 출력: 1초 상위 20 스냅샷(TTL 7일) + 1분 통계(TTL 365일). 원문 증분은 Kafka 1일만.
- 이것이 "키별 상태 + 순서 보장 + 재동기화"가 있는 진짜 스트림 잡이고, Upbit 호가(전체 스냅샷)와 대비된다.

### 3-4. 규칙과 정직한 한계
- 실돈 없음. 합성 없음. Binance 체결은 시세이지 우리 원장이 아니다(2층 원장과 별개).
- README 정체성이 "Upbit KRW" → "두 거래소(Upbit KRW + Binance USDT)"로 바뀐다.
- 총 유입 ~1,000/s 에서도 단일 호스트다. "분산 처리"가 아니라 "파티셔닝·병렬·상태 설계"라고 말한다.
