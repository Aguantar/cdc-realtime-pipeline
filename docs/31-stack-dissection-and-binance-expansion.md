# 31. 스택 해체 분석과 Binance 실시간 확장 (2026-09-20)

> 사용자: "각 스택이 진짜 제대로 일하는지 꼼꼼히 해체 분석하고 build 시작. 분산 처리의 의미가 다시 살아나야 하나?"
> 원칙: 수치는 전부 실측(09-20 00:10~00:40 UTC, 일요일 오전 KST — 한 주 중 가장 조용한 시간대라 하한으로 읽는다).

## 1. 지금 각 컴포넌트가 하는 일 — 실측으로 해체

| 컴포넌트 | 지금 받는 양 | 실제로 하는 일 | 일하는가 (냉정) | 한계는 어디서 오나 |
|---|---|---|---|---|
| **producer(Upbit WS→MySQL)** | 체결 36/s(24h 평균), 피크 ~140/s | 배치 INSERT IGNORE, 기동·재연결 gap-fill, 시각 3개 기록 | 예. 원장의 유일한 쓰기 경로 | 처리 상한 2,500/s(실측). 병목 아님 |
| **MySQL** | 36 rows/s 쓰기 + 2층 원장 수백/일 | 원장(체결 시각 일 파티션, 7일), binlog(ROW, 30일) 생성 | 예. 하지만 CPU 는 놀고 있다 | 컨테이너 메모리 986MiB/1GiB(버퍼 풀 512M). 대량 정렬이 겹치면 위험 |
| **Debezium ×2** | 체결 36/s, 원장 수백/일 | binlog → JSON 봉투. 체결은 삭제 스킵(보관소), 원장은 삭제 유지(거울) | 예. 지연 p50 3ms | 태스크 1개 고정. 체결 300/s 를 넘어도 실측(docs/23 5,000/s)상 여유 |
| **Kafka(1 broker)** | 체결 3p 9.6GiB, 호가 6p 8.8GiB, 원장 4토픽 | 오프셋 재개·다중 소비자·키 순서(market 키 뒤 재정렬 8.09%→0%) | **로그로는 일한다. 분산으로는 안 한다**(RF1, 파티션 총 105 를 브로커 1대가) | 19k~65k msg/s 실측 상한(docs/23). 우리 총 유입 ~270 msg/s = 상한의 0.4~1.4% |
| **Flink(TM 1, 슬롯 4/4)** | CDC 잡(체결 36/s, 병렬 2), 호가 잡(232/s, 병렬 1), 서킷 잡(타 프로젝트, 병렬 1) | CDC: 파싱·DLQ·24h 링 상태(마켓별 1,500분)·타이머 판정·JDBC 배치. 호가: 이벤트 시간 1분 창 집계 | **호가 잡은 일한다**(232/s, 1KB 스냅샷, 이벤트 시간 워터마크). CDC 잡은 볼륨(36/s)보다 **상태와 정확성**(exactly-once 복원, 세이브포인트 재배포 6회 trade_id 연속) 때문에 존재 | 슬롯 4 = 코어 4 이고 전부 사용 중 → 새 잡을 넣으려면 슬롯을 늘려야 한다. TM 힙 840MiB/2.25GiB |
| **ClickHouse** | 체결 3.1M/일(36.2B/행), 호가 20M/일(38.5B/행), 총 116M+131M 행 | RMT 중복 제거, 체결 시각 파티션 프루닝(1h 조회 39/39→5/56), Kafka 엔진으로 원장 소비, dbt 15모델, 대조·규칙 평가 | 예. 머지 10분 385회·평균 41ms, CPU 8.6% | 서버 메모리 1.75GiB(쿼리 1.12GiB) — 큰 집계는 일 단위로 나눠야 한다(docs/25·28) |
| **Airflow(5 DAG)** | 10분 헬스 11체크, 일일 대조·규칙·품질·케이스 | 대조(유실 2건 적발 이력), 자동 백필, 알림 | 예 | — |
| **dbt** | 품질 dq 8, dim 3, mart, 신호 | 정답(거래소) 대비 정밀도·재현율·동등성·3자 대조 | 예 — 이 프로젝트의 "검증"은 전부 여기 | — |
| **n8n / Grafana / Prometheus / kafka-ui** | — | 알림 이중화, 대시보드 2, Airflow 운영 지표, 토픽 UI | Grafana 예. **n8n 은 Airflow 와 중복, Prometheus+statsd(300MB)는 대시보드 1개용, kafka-ui 는 장식** | 컨테이너 ~20개 중 3~4개는 끌 수 있다 |

**해체의 결론**: 정확성 장치(Debezium 두 모드·RMT·대조·동등성)는 볼륨과 무관하게 일하고 있다. 볼륨으로 일하는 것은 호가 경로뿐이고, Kafka 상한의 1%, Flink 슬롯의 1/4, ClickHouse 쓰기의 극히 일부만 쓰고 있다. "Flink 가 의미 있는 파이프라인"이라는 처음 목표에 비추면 **체결 경로의 볼륨이 빈 자리**다.

## 2. 분산 처리의 의미는 다시 살아나야 하나
- **아니다, 그러나 병렬·파티셔닝 설계는 살아난다.** Binance 를 붙여도 총 유입은 ~1,000 events/s 다. 코어 4개 미니PC 하나에서 브로커·TM 을 늘리는 건 여전히 형식이다(docs/24 결론 유지).
- 대신 처음으로 **파티션 수 = 병렬도 = 키 분포**를 설계해야 한다: 체결 토픽 6 파티션(키=symbol, 683 심볼이 6개에 해시 분포), Flink 소스 병렬 3(슬롯 4→6), 싱크 배치 1,000/3s(docs/23 의 병목 근거). 호가 재구성(2단계)은 심볼별 키 상태(호가장)라 keyBy 가 실제 의미를 가진다.
- 분산이 필요해지는 지점은 docs/23 그대로: 5,000/s 부터 소스 체인 busy 1.0 → 그때 순서는 파티션 → 병렬도 → 그 다음이 브로커·TM 추가.

## 3. Binance 실시간 확장 설계 (1단계: 체결, 2단계: 호가 재구성)
### 3-1. 실측 (09-20 00:35 UTC, 30초 구독)
| 스트림 | 심볼 | msg/s | KB/s |
|---|---|---|---|
| trade | 상위 20 | 123 | 20 |
| aggTrade | 상위 20 | 62 | 12 |
| depth@100ms(증분) | 상위 20 | 129 | 54 |
| depth5@100ms | 상위 20 | 121 | 48 |
| 24h 체결 수(REST) | 상위 20 / 50 / 전체 683 | 164 / 243 / **361**/s | — |
연결 규칙(문서): 연결당 1,024 스트림, 수신 명령 5/s, IP 당 5분에 300 연결, 24시간마다 끊김, 서버 ping 20초.

### 3-2. 1단계 — 체결 전 심볼 (오늘)
| 구간 | 설계 | 왜 |
|---|---|---|
| 수집기 `binance-collector` | exchangeInfo 로 USDT·TRADING 심볼 전부(683) → `trade` 스트림을 연결당 ≤400 개로 나눠 2~3 연결, 30분마다 심볼 갱신, 23시간마다 선제 재연결, Kafka 직행(idempotent, zstd, key=symbol) | 호가 수집기와 같은 경로(원장 없음 — Binance 체결은 우리 데이터가 아니라 시세). 24h 강제 단절을 기다리지 않고 먼저 끊어 공백을 우리가 고른 시각에 둔다 |
| 토픽 `binance.trades.v1` | 6 파티션, zstd, 3일(바이트 상한 6GB) | 병렬도 3 의 2배 여유. 361/s × 200B ≈ 6GB/일 → 3일 = 보존은 재처리 창 |
| Flink `BinanceTradeJob` | 별도 잡, 병렬 3, 파서(DLQ 사이드 아웃풋 `binance.dlq.trades` + 카운터), JDBC 배치 1,000/3s | 잡 분리 = 장애 격리(체결 잡의 24h 상태를 건드리지 않음). 배치 1,000 은 docs/23 실측 근거 |
| ClickHouse `binance_trades` | RMT(recv_ms) ORDER BY (symbol, trade_ms, trade_id), 일 파티션, **TTL 30일** | 재연결 중복을 저장 층에서. 1GB/일 이라 1년은 375GB → 30일 |
| 대조 `reconcile_binance` | 일 1회 REST `klines 1h`(응답에 "체결 수" 있음, weight 2) 683 심볼 → `binance_hourly_candles` → dbt `dq_binance_reconcile_daily`(심볼×시간 셀 우리 count vs 거래소 n) | Upbit 와 같은 방식(일봉 대신 시간봉 체결 수). 1,366 weight/일 |
| 슬롯 | TM `numberOfTaskSlots` 4→6 (TM 재시작 1회, 잡은 체크포인트에서 자동 복원) | 코어 4 지만 잡들이 IO 대기라 슬롯 > 코어 허용 |
| 감시 | health_check: Flink 잡 4, binance 적재 60초 0 알림 | — |

### 3-3. 2단계 — 호가장 재구성 (1단계 24시간 관찰 뒤)
- 상위 50 심볼 `depth@100ms` → Flink keyed state(심볼별 호가장 맵): REST 스냅샷 + `U/u` 순번 검증 + 수량 0 삭제. 순번 끊김 → 재스냅샷(카운터). 출력: 1초 상위 20 스냅샷(TTL 7일) + 1분 통계(TTL 365일). 원문 증분은 Kafka 1일만.
- 이것이 "키별 상태 + 순서 보장 + 재동기화"가 있는 진짜 스트림 잡이고, Upbit 호가(전체 스냅샷)와 대비된다.

### 3-4. 규칙과 정직한 한계
- 실돈 없음. 합성 없음. Binance 체결은 시세이지 우리 원장이 아니다(2층 원장과 별개).
- README 정체성이 "Upbit KRW" → "두 거래소(Upbit KRW + Binance USDT)"로 바뀐다.
- 총 유입 ~1,000/s 에서도 단일 호스트다. "분산 처리"가 아니라 "파티셔닝·병렬·상태 설계"라고 말한다.
