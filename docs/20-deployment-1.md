## 1. 설계가 실측으로 바뀐 것부터

### 늦은 이벤트 가드: "단조 순서"가 아니라 "적재 지연"으로
처음 권한 방식은 "이벤트 시각이 직전 상태보다 과거면 생략"이었다(임계값 없음). 구현 전에 재정렬 실측을 했다.

| 측정 | 값 |
|---|---|
| 같은 마켓 체결이 이벤트 시각 역순으로 도착하는 비율 (09-16 00:00~10:50, 898,159행) | **5.87%** |
| 역순 크기 p99 / 최대 | 2.3초 / **4.8초** |
| 원인 | 체결 토픽 3파티션을 병렬 소비 → keyBy 뒤 마켓 내 순서 미보장 |

단조 가드는 실시간 체결 6%를 탐지에서 빼게 된다 → 폐기. 대신 **행 자체의 적재 지연**(`source_ts − upbit_timestamp`)으로 판정한다.
수리 행은 구조적으로 늦고(분~일), 실시간 행은 관찰 주간 최대 7.75초다. 임계 60초는 정상의 8배이고 health_check 가 이미 "실시간 아님"으로 쓰는 값이라 새 상수가 아니다.
측정은 싱크 배치 시각(flink_ts) 기준의 근사다 — 탐지기 도착 순서 자체를 찍은 것은 아니지만 같은 파티션 병렬성에서 나온다.

### 배포 공백: "겹침 배포"가 아니라 "기동 시 gap-fill"로
docs/19 #10 은 새 컨테이너를 먼저 띄우는 겹침 배포였다. compose 의 `container_name` 고정 때문에 같은 서비스를 둘 띄우는 절차가 복잡했고,
기동 직후 "마지막 적재 체결 시각부터 지금까지"를 REST 로 메우면 같은 결과(누락 0)가 나온다. 재기동은 드물어 REST 287콜(~65초)은 무시할 비용.
상한 30분: 그보다 긴 공백은 자동으로 메울 규모가 아니고 원인 확인이 먼저다(08-19 36.9h 지연 사고). 그 경우 수동 도구를 쓴다.
